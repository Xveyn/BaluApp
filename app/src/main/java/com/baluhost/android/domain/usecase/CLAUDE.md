# Use Cases

55 files across ten subdirectories, plus one top-level orchestrator (`OfflineQueueManager.kt`). Each subdirectory groups the actions for one feature area — `power/`, `system/`, `notification/`, `files/`, `shares/`, `vpn/`, `plugin/`, `activity/`, `auth/`, `cache/` — and each file is normally a single callable action injected straight into a ViewModel. This is the layer ViewModels talk to; it exists so a ViewModel test can stub one narrow interface instead of an entire `*Api` or `*Repository`.

## Core concepts

- **The shape:** `class XUseCase @Inject constructor(...)` with `operator fun invoke(...)`, usually `suspend`. Hilt provides these automatically from the `@Inject` constructor — adding a use case never requires touching a `di/` module, only `di/RepositoryModule.kt` (or similar) if it also introduces a new repository binding.
- **Two different dependency shapes, not one.** Roughly half of these use cases (see Conventions) inject a `domain/repository/*Repository` and are a near-literal passthrough, e.g. `SendWakeUseCase.invoke() = powerRepository.sendWake()`. The other half inject a `data/remote/api/*Api`, a DAO, or a manager/service directly and do their own `try/catch` + DTO-to-domain mapping inline — the two shapes look nothing alike, and which one a given file follows has to be checked in its constructor, not assumed from the subdirectory.
- **`OfflineQueueManager.kt`** (top-level, not in a subdirectory) doesn't follow the pattern at all: it's an `@Singleton` manager with many public `suspend fun`s (`queueUpload`, `retryPendingOperations`, `cancelOperation`, CRDT merge helpers, …), not a single `invoke`. It composes `UploadFileUseCase` and `DeleteFileUseCase` internally while also injecting `OfflineQueueRepository` directly.
- **`plugin/GamingMode.kt`** is not a use case either, despite living in `domain/usecase/plugin/` and counting toward that directory's 3 files — it's an `internal object` holding the plugin's string identifiers (`PLUGIN_NAME`, `ACTION_ID`, `LANGUAGE`), shared by the two real use cases in that package.

## Conventions

- **Bypassing the repository is common, not a one-off exception confined to `plugin/`.** Of the 55 files, roughly half talk to an `*Api`, a DAO, or a manager/service directly instead of a repository: all 6 of `shares/` (there is no `SharesRepository` — `domain/repository/` doesn't define one), both of `cache/` (`ClearCacheUseCase` uses a `Context`/`OfflineQueueWorkScheduler`, `GetCacheStatsUseCase` uses `FileDao` directly), both of `auth/` (`RefreshTokenUseCase`/`RegisterDeviceUseCase` use `AuthApi`/`MobileApiFactory` + `PreferencesManager` — `AuthRepository` exists in `domain/repository/` but neither use case injects it), 6 of the 7 in `files/` (only `GetFilesUseCase` injects a repository; the rest inject `FilesApi` directly — `FilesRepository`/`FilesRepositoryImpl` exists but none of them use it), 4 of 9 in `system/` (`GetRaidStatusUseCase`, `GetSmartStatusUseCase`, `GetSystemTelemetryUseCase` inject `SystemApi`; `GetEnergyDashboardUseCase` injects `EnergyApi` + `PluginApi`), 3 of 4 in `vpn/` (`ConnectVpnUseCase`/`ImportVpnConfigUseCase` use `PreferencesManager`/`VpnConnectionManager` directly, `DisconnectVpnUseCase` uses only `VpnConnectionManager`), and both of `plugin/`. Only `activity/`, `notification/`, and `power/` are consistently repository-backed across every file. Reason this matters for a newcomer: the presence of a matching `domain/repository/*Repository` interface does not mean a given use case actually uses it — check the constructor.
- **`plugin/`'s specific precedent is `system/GetEnergyDashboardUseCase`, for calling `PluginApi` without a repository — not for bypassing repositories in general.** `GetEnergyDashboardUseCase` reads `pluginApi.getTapoPluginConfig()` to resolve which devices to aggregate, establishing that a use case may reach into `PluginApi` directly; `IsGamingModeAvailableUseCase`/`StartGamingModeUseCase` follow that same precedent for the `steam_gaming` plugin. If anyone eventually introduces a `PluginRepository`, these three call sites (`GetEnergyDashboardUseCase`'s plugin-config read, and both files in `plugin/`) are what should move behind it first.
- **A "thin passthrough" isn't actually thin once a use case skips the repository.** The framing that use case logic belongs in the repository or ViewModel holds for the repository-backed half, but every use case above that talks to an `*Api` directly ends up doing that repository's job itself — HTTP exception mapping and DTO→domain conversion happen inline. `GetSmartStatusUseCase` and `GetRaidStatusUseCase` map full DTO trees to domain models by hand; `GetEnergyDashboardUseCase` and `RegisterDeviceUseCase` contain real multi-step business logic (device aggregation across multiple power monitors; QR-token registration, token persistence, and a best-effort FCM token push), not a one-line delegation.
- **`IsGamingModeAvailableUseCase` returns `Boolean`, not `Result<Boolean>`, and swallows every exception.** This is deliberate and self-documented in its KDoc: it's a discovery call ("is this plugin still enabled and does it still expose this action?"), and the only sensible response to "cannot tell" is to hide the menu entry — there's no useful error message a `Result.Error` here could show the user.
- **`invoke` is not always `suspend`.** `ClearCacheUseCase.invoke()` and `DisconnectVpnUseCase.invoke()` are plain (non-suspend) `operator fun`, because the work underneath — scheduling a `WorkManager` job, tearing down a VPN tunnel synchronously — has no coroutine to suspend for.
- **`suspend operator fun invoke()` is not the only public surface even on "normal" use cases.** `GetCacheStatsUseCase` defines its own nested `CacheStats` result type rather than reusing a domain model, because that shape (file count, oldest/newest cache age) exists only for this one caller.

## Adding a new use case

1. Pick the subdirectory for the feature area (or add a new one if none fits); name the file `<Verb><Noun>UseCase.kt`.
2. Decide the dependency: if a `domain/repository/*Repository` already exists for this feature, inject and delegate to it (see `power/` or `notification/` for the pattern). If none exists, injecting the relevant `*Api`/DAO/manager directly is an established pattern here (see `shares/`, `cache/`, `plugin/`) — but then this use case owns the `HttpException`/`Exception` mapping and DTO→domain conversion itself, so write it accordingly rather than assuming a repository will clean it up later.
3. Expose the action as `suspend operator fun invoke(...)` returning `Result<T>` (or the natural return type — `Boolean`, a domain enum — when a `Result` wouldn't add information, following `IsGamingModeAvailableUseCase`). Only drop `suspend` if the underlying call is genuinely synchronous.
4. No DI module changes are needed for the use case class itself — Hilt resolves the `@Inject` constructor automatically. A module only needs updating if this use case also requires a brand-new repository binding.
5. Inject the use case into the consuming ViewModel's constructor.
